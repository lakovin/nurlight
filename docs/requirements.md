## 1. Назначение и границы

**Назначение.** Зафиксировать, что должна делать система Nurlight: клиентский Telegram-бот, сайт для клиентов, веб-панель оператора и AI-агент, — чтобы разработка, тесты и защита опирались на один список требований, а не на переписку в чате.

**Цель системы.** Сократить время обработки заказа и операционные затраты службы доставки за счёт автоматизации приёма заказов и единой панели управления, без комиссий агрегаторов и без потери собственной клиентской базы.

**Границы MVP.**

- Входит: каталог, корзина, оформление заказа, статусы заказа, панель оператора с ролями, уведомления клиенту, FAQ, AI-агент-консультант, статистика для руководителя.
- Не входит: онлайн-оплата, мобильное приложение, геолокация и расчёт доставки по расстоянию, казахский язык, интеграция с бухгалтерией, программа лояльности.

**Принцип архитектуры.** Единый источник правды — база PostgreSQL. Бот, сайт и панель работают с одними и теми же таблицами, поэтому заказ, созданный в боте, сразу виден оператору, а смена статуса в панели сразу видна клиенту.

## 2. Пользователи и роли

| Роль | Канал | Что делает |
|---|---|---|
| Клиент | Telegram-бот, сайт | Смотрит каталог, собирает корзину, оформляет заказ, следит за статусом, задаёт вопросы AI-агенту |
| Оператор | Веб-панель | Принимает заказы, назначает курьеров, меняет статусы, правит каталог |
| Курьер | Веб-панель / уведомления | Получает назначенные заказы, отмечает «в пути» и «доставлен» |
| Руководитель / администратор | Веб-панель | Управляет пользователями и ролями, смотрит статистику продаж и времени доставки |
| Владелец бизнеса | — | Получает отчётность, владеет базой клиентов |

Роли в панели разграничиваются через RBAC: оператор не управляет пользователями, курьер видит только свои заказы, руководитель видит всё.

## 3. Термины

| Термин | Значение |
|---|---|
| FSM | Конечный автомат диалога в боте: бот помнит, на каком шаге находится клиент |
| Корзина | Набор выбранных товаров с количеством, хранится в FSM-данных до оформления |
| Заказ | Зафиксированный в базе набор позиций с адресом, телефоном и статусом |
| Позиция заказа | Строка заказа: товар, количество и цена на момент подтверждения |
| MVP | Минимально работающая версия для защиты лабораторной |

## 5. Статусы заказа

| Статус | Кто ставит | Что видит клиент |
|---|---|---|
| `new` — Новый | Бот или сайт при создании | «Заказ принят, передали оператору» |
| `accepted` — Принят | Оператор | «Оператор подтвердил заказ» |
| `assigned` — Передан курьеру | Оператор | «Курьер назначен» |
| `in_transit` — В пути | Курьер / оператор | «Курьер выехал» |
| `delivered` — Доставлен | Курьер / оператор | «Заказ доставлен» |
| `cancelled` — Отменён | Оператор; клиент — с ограничением | «Заказ отменён» |

Правила переходов:

1. Из `new` — только в `accepted` или `cancelled`.
2. Из `accepted` — в `assigned` или `cancelled`.
3. Из `assigned` — в `in_transit` или `cancelled`.
4. Из `in_transit` — только в `delivered`.
5. Из `delivered` и `cancelled` переходов нет.

## 6. Данные

| Сущность | Ключевые поля |
|---|---|
| `Client` | `telegram_id`, имя, телефон, язык, дата регистрации |
| `Category` | название, порядок сортировки |
| `Product` | название, описание, цена, категория, `is_available` |
| `Order` | номер, клиент, статус, адрес, комментарий, сумма, источник (бот/сайт), дата |
| `OrderItem` | заказ, товар, количество, цена на момент заказа |
| `Courier` | имя, телефон, активность |
| `FAQ` | вопрос, ответ, язык |
| `SupportRequest` | клиент, заказ, текст, источник, статус, кто взял, ответ, время |
| `NotificationLog` | заказ, событие, канал, статус доставки, ошибка, число попыток |
| `OrderStatusHistory` | заказ, откуда, куда, кто и когда изменил |

Требования к данным:

- Цена позиции хранится в `OrderItem`, а не берётся из `Product` при просмотре заказа: иначе история заказов изменится после правки каталога.
- `Order.total` пересчитывается из позиций и не вводится вручную.
- Удаление товара не удаляет историю заказов: товар в заказе либо хранится ссылкой с запретом удаления, либо помечается недоступным.
- `NotificationLog`, `OrderStatusHistory` и `SupportRequest` — служебные таблицы сценариев 05–07. Они не участвуют в оформлении заказа, но нужны, чтобы разобрать спорную ситуацию, проверить доставку уведомления и увидеть, кто менял статус.

## 7. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | Бот асинхронный (aiogram 3), не блокирует обработку сообщений запросами к базе |
| NFR-02 | Заказ появляется в панели не позже чем через 2 секунды после подтверждения |
| NFR-03 | Ответ бота на действие клиента — не дольше 2 секунд при нормальной нагрузке |
| NFR-04 | Бот, сайт и панель работают с одной базой PostgreSQL, без промежуточной синхронизации |
| NFR-05 | Пароли, токен бота и API-ключи хранятся в переменных окружения, не в репозитории |
| NFR-06 | Доступ к панели — только по авторизации, с разграничением ролей |
| NFR-07 | Сайт и панель работают по HTTPS |
| NFR-08 | Резервное копирование базы не реже раза в сутки |
| NFR-09 | Ошибки бота и панели логируются, по заказу можно восстановить историю статусов |
| NFR-10 | Интерфейс панели и сайта пригоден для работы с телефона и ноутбука |
| NFR-11 | Код покрыт автотестами: как минимум создание заказа, смена статуса, проверка прав |

## 8. Ограничения MVP и принятые решения

Решения ниже приняты в сценариях `docs/scenarios/` и сведены в реестр `docs/scenarios/README.md`. Они действуют, пока команда не решит иначе.

| Вопрос | Решение в MVP |
|---|---|
| Адрес | Только текстом, без геолокации |
| Телефон | Спрашивается один раз, сохраняется в профиль |
| Номер другого человека | Сохраняется в профиль: отдельного поля телефона в `Order` нет. В дипломе — `Order.contact_phone` |
| Доставка | Бесплатна, явно показывается строкой «Доставка: бесплатно» |
| Комментарий | Необязательный, до 500 символов |
| Язык | Только русский |
| Оплата | Вне MVP |
| Отмена заказа клиентом | Только в статусе `new`; после принятия оператором — через оператора |
| Недоступные товары | Бот скрывает, сайт показывает серыми с «Нет в наличии» |
| Источник заказа | Поле `Order.source`: `bot` или `site`, видно в панели |
| Уведомления | Единый модуль `notifications`, вызывается из `OrderService.change_status()` |
| Заказ с сайта без Telegram | Уведомления в Telegram не отправляются; статус доступен на сайте по номеру и телефону |
| AI и ML | AI-агент считается ИИ-частью проекта; прогноз времени доставки — после лабораторных |

## 9. Решения по открытым вопросам

Вопросы из версии 1.0 закрыты. Полный реестр, включая решения по отдельным сценариям, — `docs/scenarios/README.md`.

| № | Вопрос | Решение | Что это меняет |
|---|---|---|---|
| 1 | Доставка: бесплатно, фиксированная или по расстоянию | Бесплатно в MVP; в сводке строка «Доставка: бесплатно» | Поле `delivery_fee` не добавляется; `total = сумма позиций` |
| 2 | Сохранять ли в профиль номер, введённый для другого человека | Да, сохраняется: в `Order` нет своего поля телефона, а курьеру нужен рабочий номер | В дипломе — `Order.contact_phone` и разделение профиля/заказа |
| 3 | Нужен ли казахский язык в MVP | Нет, только русский; поля `language` остаются в схеме | Тексты и FAQ на одном языке |
| 4 | Отмена заказа клиентом | Только в статусе `new`; дальше — через оператора | Сценарий `04-my-orders.md`, кнопка отмены скрыта после `accepted` |
| 5 | Кто отправляет уведомления о статусе | Единый модуль `notifications`, вызывается только из `OrderService.change_status()`; бот и панель сообщения сами не шлют | Сценарий `05-notifications.md`, архитектура бота и панели |
| 6 | AI-агент или добавляем ML | AI-агент считаем ИИ-частью (вариант A); прогноз времени доставки — после лабораторных | Глава про ИИ, объём работ не растёт |

**Нерешённое, но не блокирующее MVP:**

| № | Вопрос | Кого касается | Когда решать |
|---|---|---|---|
| 1 | Нужны ли фото товаров в каталоге | Нурадыл, Нурдаулет | До показа, если останется время |
| 2 | Показывать ли историю статусов клиенту в боте | Нурадыл | После защиты, вместе с доработкой «Моих заказов» |
| 3 | Отвечать ли клиенту на сайте в чате или только в боте | Нурдаулет, Нурадыл | Неделя с 23 ноября |
| 4 | Нужен ли SMS/WhatsApp для клиентов без Telegram | Ислам, Нурдаулет | После лабораторных |

## 10. Критерии приёмки MVP

Система считается готовой к защите, когда:

1. Новый клиент проходит путь «каталог → корзина → оформление → заказ» в боте и на сайте, заказ появляется в панели.
2. Оператор принимает заказ, назначает курьера и доводит его до «Доставлен», клиент получает уведомления на каждом шаге.
3. Заказ с сайта и заказ из бота неразличимы по обработке, отличается только поле источника.
4. AI-агент отвечает на 15–20 проверочных вопросов, не выдумывает цены и предлагает оператора там, где не знает.
5. Руководитель видит статистику по заказам и выручке за период.
6. Пройдены тест-кейсы из сценариев `docs/scenarios/01`–`07` и автотесты панели.
7. Нет известных ошибок, блокирующих оформление заказа.
