# Бот: как устроен и как с ним работать

Памятка для разработчика бота (и для тех, кто будет его дорабатывать).

## 1. Запуск и проверка

```powershell
venv\Scripts\activate
pip install -r requirements.txt
```

В `.env` в корне репозитория нужны `BOT_TOKEN`, `DATABASE_URL` и (для виртуального оператора)
`GEMINI_API_KEY`. Полный список переменных — в [README](../README.md).

- **Разработка на SQLite:** `DATABASE_URL=sqlite:///db.sqlite3`, тестовый бот со своим токеном, затем
  `cd admin_panel; python manage.py migrate; python manage.py seed_demo`.
- **Общая база (Neon):** бот и панель используют одну базу. Запускать бота на Neon можно только
  тогда, когда миграции из кода уже применены к Neon (см. раздел 7), иначе бот упадёт на заказах.
- Запуск бота из корня репозитория: `python -m bot.main`. Один токен нельзя запускать в двух местах сразу.
- Геолокацию Telegram на компьютере отправить нельзя, оформление заказа проверяйте с телефона.

Автотесты (временная SQLite, боевая база не затрагивается):

```powershell
python -m unittest discover -s bot/tests -t . -v
python -m bot.tests_i18n        # только проверка переводов
```

## 2. Структура

```
bot/
├── main.py          # запуск: роутеры, определение языка, фоновая проверка статусов заказов
├── i18n.py          # все тексты на ru/kk/en и функция t("ключ")
├── middlewares.py   # язык клиента кладётся в current_lang перед каждым обработчиком
├── states.py        # состояния оформления: геолокация → уточнение → телефон → комментарий → проверка
├── handlers/        # один файл — один раздел: start, catalog, cart, order, my_orders, payment, faq, ai_agent
├── keyboards/       # кнопки и CallbackData; тексты кнопок берутся из i18n
├── services/        # всё, что работает с базой и внешним миром
└── tests/           # автотесты
```

**Таблицы бот не описывает.** Модели лежат в `admin_panel/delivery/models.py`, бот подключает их
через `bot/services/db.py`. Поэтому:

- в обработчиках работаем с базой только через функции из `bot/services/`;
- используем асинхронные методы ORM (`aget`, `acreate`, `afirst`, `async for`), а синхронные
  транзакции оборачиваем в `sync_to_async`;
- нужно поле, которого нет, — не создаём свою таблицу: договариваемся и меняем модель вместе с миграцией (раздел 7).

## 3. Языки (ru, kk, en)

- Язык клиента хранится в `Client.language`. При первом `/start` бот предлагает выбрать язык, позже
  его меняют командой `/language` или кнопкой «🌐 Язык».
- В коде текст всегда берётся так: `t("ключ")`. Язык определяется автоматически (`middlewares.py`).
  Вне обработчиков (уведомления) язык передают явно: `t("ключ", lang)`.
- **Как добавить новый текст:** добавить ключ в `TEXTS` в `bot/i18n.py` со всеми тремя переводами,
  плейсхолдеры (`{number}`, `{amount}`) в переводах одинаковые. Проверка: `python -m bot.tests_i18n`.
- Кнопки меню должны работать на любом языке: в фильтрах используйте `F.text.in_(CART_BUTTONS)` и
  подобные множества из `bot/keyboards/main_menu.py`, а не сравнение с одной строкой.
- **Названия и описания товаров и категорий** хранятся в базе. Русский текст — в `name` и `description`,
  переводы — в полях `name_kk`, `name_en`, `description_kk`, `description_en` (в панели: раздел
  «Переводы для бота» у товара и категории). В боте их показывает `localized(obj, "name")` из
  `bot/i18n.py`; если перевода нет, показывается русский текст. Чтобы разом заполнить переводы для
  известного каталога, выполните `python manage.py fill_translations` (в папке `admin_panel`): команда
  заполняет только пустые поля и не перезаписывает введённое. Новые товары переводят в панели.
- Казахские тексты нужно проверить носителю языка.

## 4. Оформление заказа

Путь клиента: каталог → корзина (хранится в FSM) → «Оформить заказ» → **геолокация** (кнопка
`request_location`, адрес текстом не принимается) → уточнение адреса (подъезд, этаж; можно пропустить)
→ телефон (контакт, ручной ввод или сохранённый номер) → комментарий → проверка → подтверждение.

- Корзину перед подтверждением сверяют с базой: недоступные товары убираются.
- Заказ создаётся в одной транзакции (`services/orders.py`), цена каждой позиции фиксируется в `OrderItem.price`.
- Доставка входит в сумму заказа: 500 ₸, бесплатно от 5 000 ₸ (настройки `DELIVERY_FEE`, `DELIVERY_FREE_FROM`).
  Сумму считает модель (`Order.recalculate_total`), бот показывает те же числа (`services/delivery.py`).
- Команда или кнопка меню во время оформления прерывает его, корзина сохраняется
  (`CheckoutInterruptMiddleware` в `handlers/order.py`).
- Двойное нажатие «Подтвердить» не создаёт второй заказ (блокировка на пользователя + проверка состояния).

## 5. Оплата

Один счёт на весь заказ (блюда + доставка). Логика проверок и отметки оплаты — в
`admin_panel/delivery/payments.py` (Нурдаулет), выставление счёта — в `bot/services/payment.py`.

| Режим | Как включить | Что делает |
|---|---|---|
| Настоящая оплата | `PAYMENT_PROVIDER_TOKEN` с `TEST` (токен выдаёт @BotFather, провайдер с кнопкой «Connect … Test») | бот выставляет счёт Telegram, платёж подтверждается через `pre_checkout_query` и `successful_payment` |
| Демо | `PAYMENT_DEMO=1`, токена нет | кнопка «Оплатить (тест)» отмечает заказ оплаченным **без списания денег**, номера платежа начинаются с `demo-` |
| Выключена | ничего не задано | бот показывает «Онлайн-оплата скоро появится» |

Важно: в демо-режиме на общей базе любой клиент «оплатит» заказ бесплатно, включайте его только для показа.
Минимальный платёж Telegram — 518 ₸. Оплаченный заказ клиент отменить не может, возврат оформляет оператор.

## 6. Уведомления, «Мои заказы», виртуальный оператор

- **Уведомления** (`services/notifications.py`): раз в 10 секунд (если есть активные заказы моложе 3 часов,
  иначе раз в час, см. [hosting.md](hosting.md)) бот сравнивает статусы активных заказов
  в базе с последними известными и пишет клиенту об изменении на его языке. Работает при любой смене
  статуса (в том числе массовых действиях в панели). Ограничения: известные статусы хранятся в памяти бота,
  поэтому изменения, которые произошли, пока бот был выключен, не отправляются; журнала отправок пока нет.
  Если клиент заблокировал бота, повторов нет. Запускайте **один** экземпляр бота, иначе будут дубли.
- **«Мои заказы»:** последние 10 заказов, карточка с составом и суммами, кнопка обновления,
  отмена только пока заказ «Новый» и не оплачен (одним условным обновлением, без гонки с оператором).
- **Виртуальный оператор** (`services/ai_agent.py`): Gemini, в подсказку подставляются факты о магазине,
  каталог (с пометкой «нет в наличии»), FAQ и заказы **этого** клиента (без адреса и телефона).
  Он только консультирует: корзину не собирает и заказы не меняет. Сигнатуру `ask_ai(question, history,
  client_context, language)` менять осторожно: её использует модуль сайта.

## 7. Работа с репозиторием и общей базой

- Коммиты и push делает автор изменений; в сообщении коммита только его имя (без `Co-Authored-By`).
- Перед работой — `Fetch origin` и `Pull`, перед пушем — запустить автотесты.
- Один коммит — одна законченная вещь, а не «правки».
- `.env` и `*.sqlite3` в git не попадают, токены и ключи никому не отправляем и не показываем на скриншотах.
- **Модели (`admin_panel/delivery/models.py`) меняем только после согласования с Нурдаулетом и вместе с миграцией.**
  Порядок слияния при изменении модели: сначала код модели и миграция вместе с кодом бота, который
  с ними работает, затем Нурдаулет применяет миграцию к общей базе (Neon). Если применить миграцию
  без нового кода бота (или наоборот), бот упадёт на заказах: так уже было с удаляемыми полями доставки.
- Бота на Neon запускаем только после того, как миграции применены.
